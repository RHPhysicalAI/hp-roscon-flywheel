## Review: Red Hat Platform / GitOps Correctness

**Files reviewed:** 53 | **Reviewer:** platform-agent

### Critical

- **[argocd/storage-app.yaml, operators-app.yaml, operators-config-app.yaml, minio-app.yaml, flywheel-app.yaml, observability-app.yaml, rhem-app.yaml, tekton-app.yaml]** -- None of the 9 bootstrap `Application`s carry `metadata.finalizers: [resources-finalizer.argocd.argoproj.io]`. This is the exact gap `DECISIONS.md` D075 already hit and flagged in writing: deleting `act-serving` (no finalizer, `prune: false`) orphaned its `Deployment`/`Service` objects instead of cascading, and D075's own text says "the other bootstrap apps (`argocd/*-app.yaml`) should be checked for the same missing finalizer before any of them is ever deleted." A `grep -rn finalizer argocd/` across the current tree returns nothing -- the ride-along was never done.
  **Fix:** Add `metadata.finalizers: ["resources-finalizer.argocd.argoproj.io"]` to all 9 `Application` manifests so `oc delete applications.argoproj.io <name>` cascades to the managed resources, matching the `prune: true` policy already declared in `spec.syncPolicy`.

- **[gitops/operators-config/securesign.yaml:12, argocd/operators-config-app.yaml]** -- `Securesign/securesign` targets namespace `trusted-artifact-signer`, but nothing creates that namespace: there is no `Namespace` resource for it anywhere in `gitops/`, and `operators-config-app.yaml` is the only one of the app-of-app manifests with no `syncOptions: [CreateNamespace=true]` (every sibling app has it). Even adding that flag wouldn't fix it -- `CreateNamespace=true` only creates the Application's own `spec.destination.namespace` (`flywheel`), not an arbitrarily-namespaced resource inside the manifest set. On the fresh Fury SNO bring-up that Phase 4.5-G requires, `oc apply -f argocd/operators-config-app.yaml` will leave the `Securesign` CR permanently `ComparisonError`/stuck (namespace not found), and `argocd/README.md`'s bootstrap order doesn't call out a manual `oc create namespace trusted-artifact-signer` step anywhere.
  **Fix:** Add an explicit `Namespace/trusted-artifact-signer` manifest to `gitops/operators-config/` (sync-wave `"0"`, ahead of `securesign.yaml`'s wave `"1"`), or document a hand-created-namespace step in `argocd/README.md`'s bootstrap table the same way hand-created Secrets are documented.

- **[gitops/minio/minio.yaml:67, gitops/minio/minio-readonly-user.yaml:59, gitops/flywheel/so-arm-sim.yaml:32, gitops/storage/local-path-provisioner.yaml:95, gitops/flywheel/manifest-consumer.yaml:71]** -- Five floating `:latest`/`:latest`-equivalent image tags remain in `gitops/`, contradicting the project's own stated rule ("no `:latest`", cited explicitly in `gitops/tekton/buildah-cross-arch-task.yaml` and `DECISIONS.md` D022/D112, both of which digest- or version-pin everything). `quay.io/minio/minio:latest` and `quay.io/minio/mc:latest` back the stateful object store and its credential-setup Job; `quay.io/jary/soarm-flywheel:latest` backs the core episode producer (`so-arm-sim`) -- the same repo the signed, digest-pinned `runtime-image` Tekton pipeline pushes to, so an unpinned re-pull of this Deployment can silently diverge from the image the RHEM Fleet's trust chain enforces. `registry.access.redhat.com/ubi9/ubi-minimal:latest` is baked into the local-path-provisioner's `helperPod.yaml` template. Only `manifest-consumer.yaml`'s `python-312:latest` is a knowingly-tracked deferral (D066/D068, deliberately left for a later PR to avoid a promotion-commit conflict); the other four are undocumented.
  **Fix:** Pin `quay.io/minio/minio` and `quay.io/minio/mc` to a specific release tag or digest; pin `so-arm-sim`'s image to the Tekton-built, cosign-signed digest (the same one the Fleet pins) rather than a mutable `:latest`; pin the local-path-provisioner's embedded helper-pod image; land the already-tracked `manifest-consumer.yaml` pin per the D066/D068 follow-up.

### Warning

- **[gitops/tekton/qemu-binfmt.yaml:50-51]** -- The DaemonSet's `nodeSelector: {kubernetes.io/arch: amd64}` only registers the qemu `arm64` binfmt handler on amd64 nodes. That's correct for the desktop SNO (amd64 node building an arm64 leg under emulation), but on the Fury SNO -- an all-aarch64 cluster, per `PROJECT-BRIEF.md` -- this DaemonSet will never schedule anywhere, so the qemu handler needed for the pipeline's *amd64* leg is never registered. D105 documents the digest pin and the idempotent registration but doesn't address the target-arch reversal. Since the project explicitly commits to building multi-arch on both boxes ("Desktop is x86_64; Fury is aarch64 -- build multi-arch from the start"), the `runtime-image` Pipeline's amd64 build leg will fail on the Fury as currently written.
  **Fix:** Make the DaemonSet's `nodeSelector`/registered-arch pair conditional on the cluster's node arch (e.g. two variants, or drop the `nodeSelector` and register whichever foreign arch differs from `kubernetes.io/arch` at runtime), and add a Fury-specific verification step alongside the existing desktop one in `docs/eval-records/runtime-image-tekton.md`.

- **[gitops/flywheel/edge-kafka.yaml:49-55]** -- The Kafka container runs with both `securityContext.privileged: true` and `runAsUser: 0` at the pod/container level, with no comment explaining why (unlike every other privileged workload in this repo -- `buildah-cross-arch-task.yaml`, `qemu-binfmt.yaml`, `local-path-provisioner.yaml` -- which all carry an explicit rationale for the escalation). A single-broker KRaft Kafka writing to a `hostPath` volume typically needs only a permissive SCC (e.g. `anyuid`/`hostmount-anyuid`) for the UID/hostPath mismatch, not full `privileged`.
  **Fix:** Confirm whether `privileged: true` is load-bearing (e.g. for `chcon`/SELinux relabeling on the hostPath dir, similar to the local-path-provisioner's documented reason) and either drop it in favor of a narrower SCC or add the same kind of justification comment the rest of the repo uses for privileged workloads.

### Suggestion

- **[gitops/flywheel/curator.yaml:189, sync-agent.yaml:110, rejected-mirror.yaml:77]** -- These three use the mutable tag `docker.io/library/python:3.12-slim` rather than a digest pin, unlike the careful digest-pinning discipline shown throughout `gitops/tekton/*` and `gitops/operators-config/model-registry.yaml`. Not `:latest`, so lower priority than the Critical list, but still not reproducible across a fresh Fury bring-up if upstream re-pushes the `3.12-slim` tag.

### Positive

- **[gitops/tekton/*.yaml, gitops/operators-config/model-registry.yaml:46, gitops/tekton/qemu-binfmt.yaml:62,73]** -- Excellent digest-pinning discipline everywhere the runtime-image build/sign path touches: buildah, cosign, qemu-binfmt, ubi-minimal and the MariaDB image are all pinned by `sha256` digest, and the buildah Task itself asserts "no `:latest` is ever pushed" for its own output tag.
- **[argocd/rhem-app.yaml]** -- Thoughtful, evidence-based handling of Argo CD's `helm template` vs. Helm `lookup` limitation: every lookup-derived value the flightctl chart needs is pinned explicitly, and the four generated Secrets plus the OAuth ConfigMaps are protected from re-randomization via `ignoreDifferences` + `RespectIgnoreDifferences=true`, with clear comments on why each entry exists.
- **[gitops/rhem/fleet-act-inference.yaml, gitops/rhem/README.md]** -- The Fleet manifest documents its own validation against the real flightctl v1.3.0 OpenAPI schema and a dry-run render on RHEL 10.2/podman 5.8.2 for three label combinations before ever being applied -- unusually rigorous pre-flight verification for a CR shape most teams would guess at.
- **[gitops/operators-config/model-registry.yaml, dsc.yaml, dspa.yaml]** -- Correct RHOAI sequencing via `argocd.argoproj.io/sync-wave` (DSCI wave 0 → DSC wave 1 → Model Registry DB/CR/RBAC waves 2-3) with `SkipDryRunOnMissingResource=true` on CRs whose CRDs don't exist until an earlier wave's operator reconciles -- this is exactly how a DataScienceCluster-gated component should be staged under Argo.

---
**Verdict:** REQUEST_CHANGES
**Summary:** The RHEM/Tekton signing and chart-pinning work is unusually rigorous, but the bootstrap apps still carry the exact missing-finalizer gap the project already diagnosed in D075 (fixed nowhere), a fresh-cluster bootstrap break in `operators-config` (no namespace for `Securesign`), and five floating `:latest` tags including the core sim producer and MinIO -- all of which should be closed before the Phase 4.5-G fresh-SNO-on-Fury exercise.
