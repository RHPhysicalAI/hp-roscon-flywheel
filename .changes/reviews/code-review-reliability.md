## Review: Demo Reliability (SRE)

**Files reviewed:** 19 | **Reviewer:** reliability-agent

### Critical

- **`tools/host/prune_bags.py:71-77`** -- The `--yes` deletion path references an undefined variable `mf` (`if not mf: print("refusing: no manifest"); sys.exit(1)`) -- there is no `mf` anywhere in the file; the manifest set is called `ported`. Every invocation of `prune_bags.py --yes` (run automatically by `tools/host/after_assemble.sh:26-29` after each `assemble_all.sh`) raises `NameError` and exits non-zero before deleting anything. This is the automated "port-as-you-go" disk-hygiene loop that was supposed to be the durable fix coming out of the 2026-09-09 disk-fill outage (D061/D062); it silently does nothing every time it runs, so `disk-guard.sh`'s hard park-the-loop threshold (D062) is now the *only* backstop instead of the last resort it was designed to be. This variable was almost certainly renamed to `ported` during D113's lineage-aware rewrite of this same file without updating the guard clause -- i.e. the fix for one carry-over silently broke the delete path in the same commit.
  **Fix:** change `if not mf:` to `if not ported:` (the set built at line 38-43), then run `bash -n` / a dry-run against real MinIO+Kafka state to confirm `--yes` actually deletes the `ported` class before the next rehearsal.

- **`src/camera-bridge/camera_bridge.py:132-138`** -- `/health` reports `{"wrist": _latest["wrist"] is not None, "static": _latest["static"] is not None}`. `_latest[cam]` (line 26, set at line 67) is written once by the ROS subscriber callback and never cleared or timestamped, so once a single frame has ever arrived, `/health` returns `200`/`true` forever -- even if the Gazebo sim freezes and the topic goes silent for the rest of the show. This is the same "presence, not liveness" shape as the tracked D113 `healthcheck.sh` gap, but on the very first thing the audience sees: `docs/DEMO_RUNBOOK.md`'s Beat 1 "If it breaks" flow (lines 263-269) is written to trust exactly this endpoint -- `curl .../health` returning 200 is documented to mean "bridge up; reload the tab" -- so a frozen sim during Beat 1 will send the presenter down a dead-end fix (reload) instead of the correct one (`docker restart so-arm-sim`), burning time in the tightest, highest-visibility beat of a 5-minute booth demo.
  **Fix:** stamp `_latest[cam]` with a timestamp on every frame and have `/health` report freshness (e.g. `age_s < 2`) rather than mere presence; update the runbook's Beat 1 recovery line to key off the new field.

- **`gitops/rhem/fleet-act-inference.yaml:209`** vs. **`DECISIONS.md` D113** -- D113's fix to `coordinator.py`'s `_write_eval_results` (exclude `goal_accepted: false` rows from the eval aggregate, so a wedged action server can't silently sink a real candidate's paired eval) is explicitly recorded as baked into `coordinator.py` at Tekton build time but **not live**: "not live until the next Tekton runtime-image build + sign + Fleet re-pin ... deliberately not triggered here." The Fleet's currently pinned runtime digest (`sha256:3d67f4246fd0...`, tag `act-inference-aa7392f`) predates that fix. So today, the exact wedged-action-server scenario D063 already observed once (2188 silent "Goal rejected" lines during the disk outage) would, if it recurred during a live eval-gate run, still count every subsequent episode as `task_success: false` at 0 cubes and could flip a real PASS to FAIL -- directly undermining the gate the whole narrative leans on ("the gate isn't decoration," `docs/DEMO_RUNBOOK.md:351`).
  **Fix:** either trigger the Tekton runtime-image rebuild + sign + Fleet re-pin before ROSCon so the deployed image matches `coordinator.py` HEAD, or explicitly re-open this as a tracked pre-show blocker rather than a closed carry-over -- D113 currently reads as resolved when the live artifact isn't.

- **`docs/demo-kit/README.md:28-31`** -- The contingency kit's actual recordings and screenshots -- the full Short Cut screen recording ("non-negotiable," `docs/DEMO_RUNBOOK.md:122`), the Beat 1 arm clip, Beat 2 dashboard recording, Beat 3 terminal screenshot, Beat 4 chart PNG, and the entire Beats 5/6 RHEM clip set (`rhem-kit-script.md`, including rollback and negative-trust clips) -- are all still listed under "Still to capture." Today the kit is text/JSON artifacts only. Given the stated plan of record is "nothing live is promised at the booth ... the demo must stand on contingency recordings and durable artifacts" (D023, runbook line 10-14), the "Catastrophic (no desktop, no Fury, no link)" row of the Failure recovery table (`docs/DEMO_RUNBOOK.md:691`) currently has no visual fallback for the moments that carry the story (the arm moving, the rollout, the merge, the Fleet flip) -- only markdown and JSON, which is a materially weaker fallback than what the plan of record promises.
  **Fix:** treat kit-recording capture as the top scheduling priority before ROSCon (it's already flagged "Phase 4 item 2") -- block time for the kit session referenced throughout the runbook, since every other contingency in the table assumes these clips exist.

### Warning

- **`src/inference-coordinator/coordinator.py:466-475`** -- The production loop's action-goal-rejection path (as opposed to eval mode, which D113 fixed) has no counter, backoff, or externally visible signal -- just `get_logger().warn(...)` and a 2-second retry sleep, forever. This is the identical failure signature D061-D063 already produced once (2188 "Goal rejected" lines with the arm frozen and nothing surfacing it). `healthcheck.sh` won't catch it (D113, tracked) and neither will the dashboard (`gitops/flywheel/dashboard.yaml` has no field for rejection counts). During Beat 1/Full Live, a wedged server would present as an arm that's merely "between episodes" until someone reads the container log.
  **Fix:** publish a rejection counter (or last-rejection timestamp) the dashboard and/or `healthcheck.sh` can read, and have the coordinator escalate (e.g. cancel-all-goals, per D063's own suggested cheapest fix) after N consecutive rejections instead of retrying silently forever.

- **`src/host-runner/host_runner.py:52-53`** -- `sys.exit("host_runner: MINIO_ACCESS_KEY and MINIO_SECRET_KEY must be set ...")` is called at module scope, but `sys` is never imported (only `glob, io, json, os, shutil, subprocess, tarfile, tempfile, time` are). Missing MinIO credentials raise `NameError: name 'sys' is not defined` instead of the intended clean message. Functionally the process still exits non-zero either way, but under time pressure at the booth a misleading traceback instead of the documented refusal message costs debugging time on the one component (`Host runner not resident`, runbook Failure recovery table) that's already flagged as a recurring rough edge.
  **Fix:** `import sys` at the top of `host_runner.py`.

- **`gitops/flywheel/dashboard.yaml:1749`** (Deployment) -- No `livenessProbe`/`readinessProbe` is defined for the dashboard container. If the Flask process hangs (e.g. a blocked Kubernetes API call in `_lineage()` or `set_env_var`), nothing restarts it automatically; the runbook's own recovery step is manual (`oc delete pod -n flywheel -l app=dashboard`, marked `[not run today]`) and depends on a human first noticing the SSE/status feed has gone stale.
  **Fix:** add a lightweight `/api/status`-based liveness probe (short timeout, a handful of retries) so OpenShift restarts a hung dashboard without operator intervention.

- **`docs/DEMO_RUNBOOK.md:163-165`** (Known screen artifacts) -- The runbook correctly tells presenters to trust the device's Applications tab / `applicationsSummary` over the Fleet's green banner (D070) for "is it actually serving." But that Applications-tab health is itself sourced from `healthcheck.sh` (`docker/healthcheck.sh`) -- the same probe D113 already documents as blind to a wedged action server. The runbook's own recommended "ground truth" fallback doesn't actually escape the blast radius of the tracked gap; both signals (banner and Applications tab) can read green while the arm is wedged.
  **Fix:** when citing the Applications tab as the trustworthy signal, the runbook (or a Q&A note) should say explicitly that it inherits `healthcheck.sh`'s known blind spot, so an operator doesn't over-trust it as an independent check during a live failure.

### Suggestion

- **`tools/host/disk-guard.sh`** -- The `MIN_FREE_GB=100` / `POLL_S=60` margin is comfortably sized against the measured D061 fill rate (~95 GB/hour), so the guard itself looks durable. But with the automated prune path broken (see Critical, `prune_bags.py`), free space will only ever go down between now and ROSCon rehearsals -- the guard will trip for real, more often than the "port-as-you-go" design intended, until the `mf`/`ported` bug is fixed.

### Positive

- **D023's "nothing live is promised" plan of record** (`docs/DEMO_RUNBOOK.md:10-14`) is a genuinely mature call for a first-time booth demo: the Short Cut is the plan of record, Full Live is explicitly conditional on same-day rehearsal, and every beat names its recorded stand-in. Framing contingency as the default rather than a backup is the right instinct for "tight and reliable."
- **`tools/host/run-coordinator.sh:44-56`** refuses to start the collection loop at all without `disk-guard.sh` resident and without `MIN_FREE_GB` of headroom -- a hard fail-closed precondition, not just a warning, directly traceable to the 2026-09-09 outage postmortem (D062).
- **`src/inference-coordinator/coordinator.py:666-722`** (D113's eval-mode fix) is a good example of the "diagnose the cause, not just the symptom" instinct the outage should have taught: it distinguishes a serving fault (`goal_accepted: false`) from a real policy failure so a wedged server can't silently corrupt the paired eval gate's success-rate math -- exactly the kind of scanner-backed rule this review's own severity ranking rewards. (Its gap is that the fix isn't deployed yet -- see Critical above.)
- **`docs/DEMO_RUNBOOK.md`'s "Known screen artifacts" section** (lines 161-183) narrates real, previously-observed quirks (Fleet banner racing app health, dashboard badge lag, trigger bar reset) instead of hiding them -- this is exactly the kind of honest, rehearsed-failure documentation that keeps a live demo from surprising the presenter.

---
**Verdict:** REQUEST_CHANGES
**Summary:** The contingency-first design philosophy is sound, but three concrete, previously-undetected bugs undercut it: automated bag pruning silently no-ops (`NameError` on every run), the camera health check can't detect the exact failure mode its own runbook tells presenters to rule out with it, and the fix for the one already-experienced live incident (wedged action server) isn't in the deployed image yet. Combined with the still-unrecorded contingency-kit clips, these should be closed before the next full rehearsal.
