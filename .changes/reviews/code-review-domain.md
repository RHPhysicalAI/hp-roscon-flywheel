## Review: ROS/Robotics Domain Credibility

**Files reviewed:** 17 | **Reviewer:** domain-agent

### Critical
- **[src/episode-emitter/episode_emitter.py:33,271-273,288-289]** -- `_end_episode()` rolls a random number (`FAILURE_RATE`, default `0.1`) and, if it hits, overwrites the *ground-truth* result: `task_success = task_success and not has_failure` and `cubes_placed = cubes_placed if not has_failure else 0`. The comment says `# Failure injection for demo`. Per D040 this emitter runs live in the `so-arm-sim` host container and POSTs directly to the curator (`http://10.0.0.49:30802/episode`) — this is not dead code from the pre-D016 scorer-fix era, it is on the path that feeds real curated training data and is what Beat 2 narrates as "scored on ground truth... not a heuristic." `gitops/flywheel/so-arm-sim.yaml:38-39` even pins `FAILURE_RATE: "0.1"` explicitly. No override to `0` exists anywhere in the repo. This means ~1 in 10 genuinely successful rollouts gets relabeled a failure and its cube count zeroed before the curator ever sees it — directly contradicting the "ground truth" claim, and it disagrees with `coordinator.py`'s own bag-keep decision (`_prune_bag_if_rejected`, which uses the real `peak_cubes` and would keep the bag), so a kept bag can carry curator metadata claiming the episode failed. A ROS engineer who reads this file after the "ground truth, not a heuristic" line in the runbook will find a coin flip that fakes the ground truth.
  **Fix:** delete the failure-injection block (or set `FAILURE_RATE=0` as the hard default and remove the env override entirely) so `task_success`/`cubes_placed` are always the values `_compute_task_success()`/peak-cube tracking actually measured; if a "demo variety" signal is still wanted, generate it visibly in the dashboard layer, never inside the data the curator/trainer consumes.

- **[src/inference-coordinator/coordinator.py:391,492,558]**, **[src/sim-reset/sim_reset.py:106]** -- Four separate "is the arm home / has it settled" checks slice the first 5 elements of `/joint_states` positions (`self._latest_positions[:5]`, `positions[:5]`) with comments claiming this skips the gripper ("First 5 are arm joints (skip gripper)", "arm joints (skip gripper)"). But `coordinator.py:94` documents, correctly, that "`/joint_states` publishes joints in a DIFFERENT (alphabetical) order" — which is *why* `CTRL_JOINTS` commands are built by name, never by index (and `_learn_rest_pose` correctly does `dict(zip(self._latest_names, self._latest_positions))`). Sorted alphabetically, the 6 joints are `elbow_flex_joint, gripper_joint, shoulder_lift_joint, shoulder_pan_joint, wrist_flex_joint, wrist_roll_joint` — so `positions[:5]` actually contains the gripper (index 1) and excludes `wrist_roll_joint` entirely. `_arm_at_home()`, the early-stop "is the arm still moving" check in `run_forever` and `_policy_window` (eval harness), and `sim_reset.py`'s `arm_is_home()` are all silently evaluating gripper motion as if it were an arm joint and never checking wrist-roll settle at all. This is exactly the kind of index-vs-name mismatch a ROS engineer is trained to distrust, and the code already contains the correct fix pattern (name-based lookup) two lines away — it just wasn't applied consistently. It's a plausible contributor to the undiagnosed `RESET_ARM=true` loop breakage noted in the `RECOVER_ON_FAIL` comment block (coordinator.py:86-89).
  **Fix:** build a `name -> index` map from `self._latest_names` (as `_learn_rest_pose` already does) and select the 5 non-gripper `CTRL_JOINTS` by name in every home/rest check, not by raw list slice.

### Warning
- **[docker/inference-entrypoint.sh:20-21]** vs **[DECISIONS.md D058/D059]**, **[docs/eval-records/phase3-ladder/*.json]** -- The deployed rosetta client chunking defaults are `ACTIONS_PER_CHUNK=100`, `CHUNK_SIZE_THRESHOLD=0.5` (D058, applied everywhere per D059). But D059 itself records that "every GPU eval in `docs/eval-records/` before this date... ran at 30/0.95" — i.e. the headline 73%→86% ladder numbers and the "18/20 CPU vs 17/20 GPU" comparison quoted in `docs/DEMO_RUNBOOK.md`'s "What is true" table were measured under different chunking parameters than what the booth actually runs. D059 flags this as an open, undocumented residual ("if a future GPU re-baseline at 100/0.5 moves the number, the ladder JSONs must state the chunk params"). None of that caveat reaches the runbook's Beat 4 script or "What is true" table — a technically sophisticated attendee who asks "were these numbers measured on the config you're actually running?" would get a no that isn't disclosed anywhere in the narration.
  **Fix:** either re-run the N=100 paired eval and the D020 CPU/GPU comparison at 100/0.5 before ROSCon, or add one line to the "What is true" table / Q&A crib noting the chunk-parameter difference, so it's a disclosed shortcut like the others (D023, D067) rather than an undisclosed one.

- **[docs/DEMO_RUNBOOK.md: "Likely questions" / Reference section]** vs **[src/episode-emitter/episode_emitter.py:271-273]** -- The runbook explains the gap between the live loop's curated/rejected ratio (~35-38% for the teacher) and the 73% clean-start eval rate entirely by "the eval homes the arm each episode; the loop does not." That's a real contributor, but it isn't the only one: the loop's `FAILURE_RATE` noise injection (Critical finding above) also suppresses the loop's apparent success rate by design, and isn't mentioned as a factor at all. Given how carefully this project otherwise attributes gaps to their real cause (D067's re-release naming, the "one honest shortcut" section), this is an unforced honesty gap once the injection is fixed or disclosed.
  **Fix:** once `FAILURE_RATE` is removed (see Critical), this note becomes moot; until then, add it to the same explanation so the two effects aren't conflated.

- **[src/inference-coordinator/coordinator.py:221-238]** vs **[src/episode-emitter/episode_emitter.py:173-195]** -- Two independent threads poll ground-truth cube pose during every episode: the coordinator's `_start_peak_poll` (`task_eval.evaluate_task()` every 2.5 s) and the emitter's `_poll_cubes` (`subprocess.run(["python3","/ws_pai/task_eval.py"])` every 2.0 s, in a *different* container). Both compute a peak-cube high-water mark independently and can legitimately disagree (different poll phase, different process each shelling out to `gz topic -e -n 1`), yet both numbers are treated as authoritative in different places (coordinator's bag-keep decision vs. emitter's curator JSON `cubes_placed`). This is the same seam that produces the data-integrity issue in the Critical finding, even without `FAILURE_RATE`.
  **Fix:** have the coordinator publish its peak-cube count to the emitter (it already publishes `dataset_path` and `model_version` this way) instead of each process re-deriving ground truth independently from a fragile CLI scrape.

### Suggestion
- **[src/episode-emitter/task_eval.py:46-86]** -- `read_cube_poses()` shells out to `gz topic -e -t ... -n 1` and regex-parses the text dump on every call (every ~2 s during an episode, from two processes per the Warning above). It fails silently to `{}` on any exception, which `evaluate_task()` then reports as `cubes_placed=0` — i.e. a transient CLI hiccup reads identically to "no cubes placed," with no way for an operator to distinguish "sensor down" from "real failure" in the curator JSON. Given this is the sole ground-truth channel the whole training/promotion story rests on, it's worth a distinguishable "unavailable" state (e.g. `None` cubes_placed, excluded rather than zeroed) rather than folding read failures into 0/3.

### Positive
- **[src/episode-emitter/task_eval.py:1-20,94-112]** -- Scoring from the Gazebo world pose topic instead of a vision/heuristic classifier is a genuinely sound "ground truth" design choice for a manipulation demo, and D016's documented root-cause fix (the `/gazebo/worlds` service not responding in this `gz` build, switched to the world-scoped pose-info topic) is the kind of concrete, verifiable debugging a ROS engineer will trust.
- **[docs/DEMO_RUNBOOK.md: "The story you're telling"]**, **[PROJECT-BRIEF.md:53-58]** -- Attribution to `ros-physical-ai/demos` is explicit, generous, and repeated at exactly the moments a skeptical audience would look for a land-grab ("The policy is upstream's; the loop that makes it improvable, measurable and governed is the story"). Nothing reviewed claims the SO-ARM101/ACT/LeRobot work as Red Hat's own.
- **[docs/eval-records/phase3-ladder/*.json]**, **[DECISIONS.md D015, D021]** -- The improvement-proof methodology (fixed seeded scenes, paired per-seed comparison, sign-test rather than a raw percentage-point claim, and — critically — reporting that fine-tuning on 20/40 curated episodes made the policy *worse* and shipping that result instead of hiding it) is real statistical discipline for a booth demo, not just a marketing chart. The N=50+N=50 JSON files sum correctly to the runbook's claimed 73/100 and 86/100 aggregates.
- **[DECISIONS.md D067]** -- The `act-v2-ft160-rhem` declared-re-release naming, and the runbook's explicit "never call it v3" instruction, is exactly the kind of self-restraint that keeps the demo's central improvement claim honest under questioning.

---
**Verdict:** REQUEST_CHANGES
**Summary:** The core self-improvement story is measured with real rigor and the upstream attribution is fair, but a live "failure injection for demo" coin-flip in the emitter that actually feeds the curator directly contradicts the runbook's "ground truth, not a heuristic" claim, and a joint-ordering bug means several arm-settle checks silently watch the gripper instead of the wrist — both are concrete, fixable issues a ROSCon-attending engineer would find on a first read of the source.
