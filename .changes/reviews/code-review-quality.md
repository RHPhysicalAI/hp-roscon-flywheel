## Review: Code Quality / Maintainability

**Files reviewed:** 31 | **Reviewer:** quality-agent

### Critical
- **[tools/host/prune_bags.py:72]** -- `if not mf: print("refusing: no manifest"); sys.exit(1)` references `mf`, a name that is never defined anywhere in the file (the manifest count is tracked in `manifests_seen`). Every invocation of `--yes` hits this line before any deletion happens, so it always raises `NameError` instead of running the retention delete. This is the script `after_assemble.sh` calls unattended after every dataset assembly, and the one that was supposed to keep bag disk usage under control after the 2026-09-09 outage — it currently cannot delete a single "ported" bag.
  **Fix:** Change `if not mf:` to `if not manifests_seen:` (that's clearly the intent — refuse to delete if no manifests were scanned). Add a smoke test that runs `--yes` against a fixture with at least one manifest and asserts bags are actually removed, so this class of bug fails CI instead of surfacing in production.
- **[src/host-runner/host_runner.py:53]** -- `sys.exit("host_runner: MINIO_ACCESS_KEY and MINIO_SECRET_KEY must be set ...")` is called at import time, but `sys` is never imported anywhere in this file (only `glob, io, json, os, shutil, subprocess, tarfile, tempfile, time, math.comb, pathlib.Path, boto3, kafka` are). Any environment missing the MinIO credentials crashes with `NameError: name 'sys' is not defined` instead of the intended clear operator message — the opposite of what this guard was written to do.
  **Fix:** Add `import sys` near the top of the file. `src/dataset-assembler/assemble_dataset.py` and `tools/host/prune_bags.py` both do this correctly for the identical pattern — worth a quick grep across the repo for other `sys.exit(` call sites missing the import.

### Warning

A repo-wide grep finds zero live references to `zenoh-connect.json5` outside `DECISIONS.md`'s historical note.
  **Fix:** Delete the file, or if it's kept as a documented reference example, add a comment stating it is not consumed by any script and pointing at the inline generator that replaced it.
- **[gitops/flywheel/dashboard.yaml:~1718]** -- The `dashboard-vllm-reader` Role still grants `services: get, list`, with its own comment admitting `"Service read is unused since act-serving was retired (D075); kept for the Deployment read"`. This is a half-finished retirement: the RBAC still over-grants a permission nobody uses instead of being trimmed to just the Deployment verbs that are actually needed.
  **Fix:** Drop the `services` resource/verbs from this Role (or split into two Roles and delete the now-dead one) so the retirement matches "verify no lingering references" rather than leaving a documented-but-unused grant in place.
- **[AI-marker inconsistency across `src/`, `docker/`]** -- The Red Hat AI-policy marker (`# This project was developed with assistance from AI tools.`) is applied inconsistently. Present and consistent in: `pipeline/act_flywheel_pipeline.py`, `src/inference-coordinator/model_version_pub.py`, `docker/healthcheck.sh`, `docker/inference-entrypoint.sh`, all of `device/`, and most of `tools/host/` + `tools/hub/`.
  **Fix:** Sweep the unmarked list above and add the one-line comment near the top of each file (Python: `# This project was developed with assistance from AI tools.`; shell/Dockerfile: same text after `#`). Worth a cheap scanner (grep for the marker string across tracked source files, allowlist non-code files) rather than relying on remembering to add it per-file going forward — this is exactly the kind of rule that should be checked mechanically, not just written down.
- **[PROJECT-BRIEF.md:84, AGENTS.md:19]** -- Both state the desktop dev-stand-in IP as `10.0.0.41`. This is a known, already-flagged staleness (not re-derived here) — the actual IP has been `10.0.0.48` for most of the project's life, confirmed current everywhere else that matters: `DECISIONS.md` D002 (records the exact change from `.4` to `.48`), `device/README.md`, `device/enroll.sh`'s default, `docs/DEMO_RUNBOOK.md` (dozens of `ssh jary@10.0.0.48` references), and `gitops/flywheel/dashboard.yaml`'s hardcoded camera host.
  **Fix:** Update both files' `10.0.0.41` to `10.0.0.48`.

### Suggestion
- **[src/inference-coordinator/coordinator.py:479-514 vs. 542-575]** -- `run_forever()`'s inline policy-attempt-window loop (rest-detection, early-stop, task-complete check) is duplicated almost verbatim in `_policy_window()`, added later for the eval harness. The two copies already show minor drift (the eval version is missing recovery/settle bookkeeping the loop version has) and will keep drifting since nothing forces them to stay in sync.
  **Fix:** Factor the shared window loop into one method both `run_forever()` and `run_eval()` call, parameterizing only what genuinely differs (recording, signaling).
- **[gitops/flywheel/dashboard.yaml:1198]** -- `const camHost = '10.0.0.48';` with an adjacent `// TODO: make configurable via env/config instead of hardcoded.` This is already tracked as a known gap in `docs/DEMO_RUNBOOK.md`'s comparison table, but it's worth surfacing here too since the Fury move (aarch64, different host IP) is exactly the scenario this hardcoding will break.
- **[THOR-TESTING-REUSE.md's `gitops/hub-training/` entry]** -- The reuse-map table lists `gitops/hub-training/` (manifest-consumer) as a 1:1 copy target, but this repo's manifest-consumer actually landed at `gitops/flywheel/manifest-consumer.yaml` — there is no `gitops/hub-training/` directory here. The doc is technically consistent (the table describes thor-testing's own layout, per the "thor-testing repo structure reference" section at the bottom), but nothing in the table itself signals that the paths are source-repo-relative rather than describing where things ended up in this repo, which could mislead a reader hunting for that directory here.

### Positive
- **[gitops/act-serving/, src/swap-agent/ retirement]** -- Genuinely clean. Both are fully removed from the working tree (no directories, no live YAML, no scripts calling them); every surviving reference is in a doc explicitly marked historical/superseded (`docs/demo-kit/README.md`: "superseded... history only"; `argocd/README.md`: "retired 2026-09-09... file removed"; `docs/eval-records/promotion-2.md`: a point-in-time record of the retirement itself). The one exception (`dashboard.yaml`'s unused `services` RBAC verb, flagged above) is minor.
- **[device/provision.sh, device/enroll.sh, device/vm/create-vm.sh, device/vm/bags-share.sh]** -- Consistently strong: idempotent by design, credential values are sourced and redacted rather than echoed, error messages tell the operator exactly what command to run next (e.g. `provision.sh`'s podman-version and virtiofsd failures), and inputs are validated against the actual downstream constraint (e.g. `enroll.sh`'s Kubernetes label-value regex, checked locally before the API would 400).
- **[src/inference-coordinator/coordinator.py rest-pose recovery logic]** -- Comments explain *why*, including dead ends that were tried and reverted (e.g. `RESET_ARM=true` via `sim_reset`'s topic-pub subprocess "broke the loop for reasons not diagnosed; this recovery publishes in-node instead"). That's the right level of detail for future maintainers to avoid re-trying a known-bad approach.

**Summary:** The reuse directive held cleanly at the code level and the retired serving path was removed without leaving live references, but two scripts on the disk-management critical path (`prune_bags.py`, `host_runner.py`) have straightforward crash bugs — the bag-pruning deletion path in particular has never actually run successfully via `--yes` given the `mf` NameError.
